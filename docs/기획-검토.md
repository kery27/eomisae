# 기획 검토

> 상태: 검토 중 · 최종 수정 2026-09-27 · MVP 플랫폼 확정(안드로이드) · 플랫폼 정보 미수집(D15)
> 개발 전 단계. 여기 적힌 기능은 모두 검토 대상이며, 구현 확정이 아니다.

## 1. 배경

배달 라이더가 픽업하는 가게에서 받는 불공정한 대우(조리 지연 방치, 폭언, 파손 책임 전가, 화장실·대기 공간 거부 등)를 개선하기 위한 라이더용 서비스. MVP는 **안드로이드 앱**으로 만든다(D9).

### 1-0. 핵심 가치

| # | 가치 | 라이더가 얻는 것 | 데이터 |
|---|---|---|---|
| ① | **지금 밀렸는지 안다** (실시간 동네 현황) | "바삭치킨 ○○점: 2명 대기 중, 가장 긴 대기 18분째" → 콜을 받을지 판단 | 동네 라이더들의 진행 중 대기 |
| ② | **가게를 보고 판단한다** (쌓인 기록) | "이 지점 최근 2주 이 시간대 대기 4건, 평균 대기 16분" | 동네 라이더들의 지난 기록 |
| ③ | **내 기록이 남는다** (개인 도구) | 업무 일지, 대기 알림, 신고용 요약 | 내 기록 |

**모든 데이터는 라이더가 가게 앞에서 직접 겪은 일(어느 가게, 언제 도착, 얼마나 기다림, 픽업/취소)뿐이다. 플랫폼 앱의 정보는 앱에 옮기지 않는다(D15).** ①·②가 서비스의 핵심이고, ③은 유저가 적은 초기에도 앱을 쓸 이유이자 ①·②의 데이터 원천이다. 신고는 ③에 딸린 부가 용도다.

**구조:** 나는 나대로 기록한다 → 그 기록이 동네 라이더들에게 실시간으로 보인다 → 다른 라이더의 기록 덕분에 나도 밀린 가게를 안다. 라이더끼리의 상생 협업이며, 유저가 늘수록 가치가 커진다. 그래서 **한 동네에 집중해서 시작**한다.

### 1-1. 조리 대기가 생기는 구조

> 전업 라이더 2년 경험 기반. 플랫폼 공식 자료로 확인 필요.

- 두 플랫폼(배민·쿠팡이츠) 모두 콜 수락 시 라이더 앱에 **조리 예정 시간**이 뜬다. 표시 문구는 플랫폼마다 다르다: 배민 "준비완료 예정시간", 쿠팡이츠 "N분 뒤 조리완료 예정".
- 이 시간은 플랫폼이 추천하고, **가게가 조절할 수 있다.** 설정은 가게 자율이다.
- 조리가 끝나면 가게가 누른 **조리완료 알림**이 라이더에게 뜬다.
- 조리가 오래 걸리면 가게는 **조리 시간을 추가로 늘릴 수 있다.** 이 기능이 있는데도 쓰지 않는 가게가 문제의 핵심이다.

공식 자료로 확인한 내용 (7장 출처 참고):

| | 배민 (알뜰·한집배달) | 쿠팡이츠 |
|---|---|---|
| 조리시간 추가 | **라이더 배차 전까지만**, 1회, 최대 30분 (5분 단위) | 수락 전 '바쁨 모드'·추가 기능으로 최대 30분, **수락 후 조리 중에도 10분 연장** 가능 |
| 조리완료 | '준비완료' 버튼 → 라이더에게 알림 | '준비완료' 버튼 |
| 연장 시 불이익 | 확인 못 함 | 쿠팡이츠 측: "조리시간에 대한 업주 패널티는 없다" |
| 플랫폼 안내 | "준비시간이 너무 짧으면 라이더를 대기하게 만들 수 있다" | - |

- 배민은 배차 뒤에는 늘릴 수 없으므로, **라이더가 콜 수락 때 본 예정 시각이 그대로 약속**이 된다.
- 쿠팡이츠는 연장해도 불이익이 없다고 밝혔다. 그런데도 늘리지 않는다는 것은 **선택**이다.

**병목은 두 종류다.** 이 서비스가 다루는 것은 두 번째뿐이다.

| | 라이더가 부족할 때 | 주방이 부족할 때 |
|---|---|---|
| 누가 기다리나 | 음식이 라이더를 기다림 | 라이더가 음식을 기다림 |
| 주로 언제 | 악천후, 라이더 적은 시간대 | 피크 타임, 주문 몰림 |
| 가게가 쓸 수 있는 수단 | - | 조리시간 늘리기, 바쁨 모드, **주문 일시정지** |

단골 중국집이 피크 때 주문을 내린 것은 주방 병목에 대한 **가장 확실하고 정직한 대응**이다. 매출을 포기하는 비용을 가게가 스스로 치른다. 상습 대기 가게는 어떤 수단도 쓰지 않고 그 비용을 라이더에게 넘긴다.

문제는 가게가 **소화할 수 없는 짧은 조리 예정 시간을 설정할 때** 생긴다.

| | 정직한 가게 (예: 단골 중국집) | 상습 대기 가게 |
|---|---|---|
| 피크 대응 | 예정 시간을 길게 잡거나 주문을 내림 | 짧게 잡은 채로 콜을 다 받음 |
| 대기 비용 | 가게 앞 마찰로 사장이 직접 치름 | 라이더가 떠안음. 거절하고 가도 다음 라이더가 옴 |
| 라이더에게 하는 말 | - | "조리완료 안 눌렀는데 왜 왔냐" |

짧게 잡는 이유로 추정되는 것: 예정 시간이 길면 라이더가 콜을 거절하고, 고객 앱의 배달 예상 시간도 길어진다.

**핵심:** 느린 것 자체는 문제가 아니다. 피크 때 튀김기 용량처럼 느릴 수밖에 없는 가게도 있다. 문제는 **느린데 빠르다고 알리는 것**이다. 라이더는 가게가 스스로 설정한 시간에 맞춰 배차되어 온 것이므로 "완료 안 눌렀는데 왜 왔냐"는 핑계가 되지 않는다.

D11·D14의 "GPS 미사용"은 MVP까지만 유효하다. | 2026-09-28 |

|  | 가게 평가 서비스 | 기록·증거 도구 + 픽업 정보 (채택) |
|---|---|---|
| 중심 | 공개 점수, 주의 가게 | 내 대기 기록, 증거, 픽업 위치 정보 |
| 치팅 유인 | 큼. 점수를 깎는 것이 곧 보복 | 작음. 공개되는 것은 모아진 사실뿐 |
| 법적 위험 | 큼 | 작음 |
| 라이더 효용 | 속은 시원함 | 분쟁 때 실제로 도움이 됨 |

공개 정보는 **측정된 대기 시간, 반복적으로 보고된 상황, 픽업 위치** 같은 모아진 사실로 제한한다. 억울한 일에 대한 대응은 **개인 기록·증거를 들고 플랫폼에 정식 신고**하는 쪽으로 유도한다.

## 3. 핵심 위험: 라이더 치팅

가장 큰 우려는 라이더들이 기분이 나쁘다는 이유로 단체로 특정 가게를 공격하거나 보이콧하는 것이다.

### 3-1. 치팅 유형

| 유형 | 예시 | 위험도 |
|---|---|---|
| 단체 보복 | 한 명이 기분 나쁜 일을 겪고 단톡방에서 "다 같이 1점 주자" | 가장 큼 |
| 과장 | 실제 10분 대기를 30분으로 적음 | 중간 |
| 다중 계정 | 한 사람이 계정 여러 개로 도배 | 중간 |
| 앱 밖 보이콧 | 앱의 가게 목록을 근거로 "이 집 콜 받지 말자" 운동 | 큼. 앱이 조직 도구가 됨. D4로 선을 긋는다 |
| 반대 방향 조작 | 가게 측의 자작 호평, 경쟁 가게 악평 | 중간 |

### 3-2. 왜 까다로운가

- **인증으로 해결되지 않는다.** 단체 보복은 진짜 라이더가 한다.
- **정당한 집단 문제 제기와 보복이 데이터상 비슷하다.** 진짜 악질 가게도 문제가 되면 제보가 몰린다. 너무 엄격하면 진짜 피해가 묻힌다.
- **법적 위험이 운영자에게도 온다.** 허위·과장 정보로 가게 영업에 피해가 생기면 명예훼손, 업무방해, 신용훼손 문제가 될 수 있다. 정식 서비스 전에 법률 검토가 필요하다.

### 3-3. 대응 방향

| 방향 | 내용 | 한계 | D1 기준 판단 |
|---|---|---|---|
| A. 별점·순위 폐지, 사실만 기록 | 1~5점 별점과 '주의 가게' 순위를 없애고, 측정된 가게 앞 대기(D3)와 구체적 상황 태그만 남긴다 | 한눈에 판단하기 어렵다 | **채택 방향.** D1과 같은 결론 |
| B. 실제 방문자만 기록 | 대기 타이머 기록 + 가게 근처 위치 확인이 있어야 공개 정보에 반영 | 위치는 조작 가능. 배달 앱 주문 연동은 불가 | 검토 필요 |
| C. 시간 분산 기준 | 서로 다른 날·시간대에 여러 라이더가 겪은 일만 반영. 짧은 기간에 몰린 기록은 보류 후 검토 | 기준 기간·인원 설정이 필요 | **가장 유력.** 진짜 문제는 흩어져 쌓이고, 보복은 몰린다 |
| D. 기록자 신뢰도 | 여러 가게를 골고루, 좋은 가게도 기록하는 사람에게 가중치. 신규·편향 계정은 낮춤 | 기준이 불투명하면 불만 | 검토 필요 |
| E. 판결이 아닌 기록으로 표시 | "주의"라는 낙인 대신 "최근 30일 기록 12건, 평균 대기 18분" 형태. 오래된 기록은 점점 흐려짐. 가게 측 해명·정정 창구 | 운영 부담 | 채택 방향 |
| F. 운영 규칙 | "다 같이 콜 거절하자" 같은 집단 행동 선동 금지. 이상 패턴 자동 보류, 신고 누적 시 가림 | 운영 인력 필요 | 채택 방향 |

### 3-4. 기록 시각 조작: 막을 수 있는 것과 걸러지는 것

라이더가 직접 누르는 버튼([대기 시작], [픽업])이라 시각을 부풀릴 수 있다.

| 조작 | 막을 수 있나 | 방법 |
|---|---|---|
| 도착 전, 달리는 중에 [대기 시작] | ✅ 막음 | 움직임 감지(D14): 탈것 이동 중에는 시작 불가 |
| 출발한 뒤에 [픽업]을 늦게 누름 | ✅ 막음 | 출발 시각과 [픽업] 중 이른 쪽을 씀(D14) |
| 받고 나서 가게 앞에서 담배·화장실 후 늦게 누름 | ❌ 못 막음 | 폰이 가게 앞에 가만히 있어 감지 안 됨. 아래처럼 걸러낸다 |

못 막는 경우가 공개 수치에 미치는 영향:

| 경우 | 걸러지나 | 이유 |
|---|---|---|
| 한 사람이 가끔 부풀림 | ✅ | 중앙값 사용, 여러 라이더 기록이 모여야 공개(3-3 C) |
| 한 사람이 늘 부풀림 | ✅ | 같은 가게에서 다른 라이더보다 늘 길게 나오는 패턴 → 가중치 낮춤(3-3 D) |
| 모두가 조금씩 부풀림 (3~5분) | ❌ 튀지 않음 | 모든 가게에 비슷하게 더해져 **가게끼리 비교**에는 영향이 적다 |
| 여럿이 짜고 특정 가게만 부풀림 | ⚠️ 약함 | 사실상 단체 보복(3-1). 시간 분산 기준, 가게 해명 창구로 대응 |

**포기 기록(D17) 지어내기:** 콜만 잡고 가게에 가지 않은 채 [안 나와서 그냥 가요]를 누를 수 있다. 버튼만으로는 현장에 있었는지 증명할 수 없다.

| 장치 | 단계 | 효과 |
|---|---|---|
| 한 사람의 포기만으로는 표시 안 함 (D18: 30분 안 2명 이상) | MVP | 혼자 지어낸 포기는 현황에 안 뜸 |
| 같은 가게 포기는 한 사람당 하루 1번만 셈 | MVP | 한 명이 도배하지 못함 |
| 누르기 직전 "이동 → 정차" 흐름 확인 (D14) | MVP | 집에 앉아서 누르는 것을 약하게 걸러냄 |
| 다른 라이더 기록과 자주 엇갈리는 계정은 가중치 낮춤 (3-3 D) | MVP | 상습적으로 지어내는 사람을 희석 |
| 포기 기록에는 보상 없음 | MVP | 지어낼 이유를 줄임 |
| **위치 확인** (D19) | 2단계 전 | 현장에 없었으면 공개 현황에 반영 안 됨. 유일하게 확실한 방법 |

여럿이 짜고 특정 가게를 찍는 것은 위치 확인 없이는 막지 못한다(3-1 단체 보복). 그래서 모르는 사람들이 들어오는 2단계 전에 위치 확인을 도입한다.

부풀릴 이유 자체도 약하다: MVP 기록은 본인에게만 보이고(실시간 현황은 대기가 끝나면 사라짐), 지원금은 플랫폼이 자기 기록으로 주며, 신고는 플랫폼 기록과 대조된다(D7). 부풀릴 이유가 생기는 것은 쌓인 기록을 공개하는 3단계뿐이고, 그때는 위 필터가 작동한다. 그래서 **보상은 대기 길이와 무관하게** 설계한다(D13).

### 3-5. 리뷰 서비스와 비교

본질은 네이버·배민 리뷰와 같다: 직접 가본 사람이 겪은 일을 다른 사람에게 알린다. 리뷰 서비스가 합법적으로 운영되고 있으니, 이 서비스의 위험도 **리뷰 서비스라면 다 안고 있는 관리 가능한 위험**이다.

| | 리뷰 서비스 | 이 앱 |
|---|---|---|
| 내용 | 별점 + 자유 글 (주관적 평가) | **숫자만** (측정된 사실). 라이더가 쓴 문장은 공개 안 함 → 리뷰보다 안전 |
| 쓰는 사람 | 손님 (소비자 보호 명분) | 라이더 (가게의 손님은 아님, 노동환경 명분) |
| 가게에 미치는 영향 | 손님들이 천천히 판단 | **실시간**, 라이더가 바로 콜을 거를 수 있음 → 더 조심 |
| 운영사 | 법무·신고 처리 체계를 갖춘 대기업 | 개인 → 절차를 미리 정해 둔다 |

리뷰 서비스의 방식을 그대로 가져온다.

| 리뷰 서비스 | 이 앱 | 단계 |
|---|---|---|
| 영수증·예약 방문 인증 | 위치 확인 (D19) | 2단계 전 |
| 신고와 임시조치 | 요청 접수 → 가리기 → 소명 → 판단 (정보통신망법 44조의2) | 2단계 전 |
| 사장님 답글 | 가게 해명·정정 창구 | 3단계 |
| 오래된 리뷰는 아래로 | 오래된 기록은 흐리게 (3-3 E) | 3단계 |

## 4. 메인 기능 후보 (D1 기준 재검토 대상)

> 이 중 MVP에 넣는 것과 뺀 것은 8장에 정리했다.

라이더가 앱을 여는 세 순간을 기준으로 삼는다.

| 순간 | 상황 | 필요한 것 |
|---|---|---|
| 배차 수락 전, 픽업 가는 길 | 몇 초, 한 손 조작 | 어디로 픽업 가는지, 대기가 긴 편인지 |
| 가게 도착 후 대기 중 | 몇 분씩 붙잡혀 있음 | 기록하기 |
| 퇴근 후 | 여유 있음 | 커뮤니티, 내 기록 돌아보기 |

| 후보 | 내용 | 비고 |
|---|---|---|
| **실시간 동네 현황** | 동네에서 지금 대기가 걸린 가게 목록. 인원, 가장 긴 대기, 경과 시간. 대기가 끝나면 사라짐 | 핵심 가치 ①. D12·D13 |
| 대기 타이머 + 내 기록 | 도착·픽업을 기록해 가게 앞 대기 시간을 잰다. 메모, 개인 업무 일지로 누적 | D1·D3의 중심 기능 |
| 픽업 정보 | 픽업 위치, 주차 위치, 화장실 가능 여부 등을 라이더들이 함께 채움 | 사실 정보라 법적 위험이 적음 |
| 가게 정보 (모아진 사실) | 시간대별 평균 대기, 반복 보고된 상황. 별점·순위 없음 | 치팅 대응 C·E 적용 필요 |
| 신고용 기록 정리 | 내 기록을 날짜·시각·대기·사진 요약으로 정리해 고객센터에 붙여넣기 | 대처법 체크리스트와 연결 |
| 신고 이력 + 개선 추적 | 내가 언제 어느 지점을 신고했는지 남기고, 신고 **전후로 그 지점의 대기 시간이 줄었는지** 보여준다 | 플랫폼이 신고 결과를 알려주지 않으므로(7-1), 앱이 그 빈자리를 채운다 |
| 대기 알림 | 라이더가 정한 시간("20분 뒤 알려줘")이 되면 떠 있는 타이머로 알린다. 지원금 기준 시각은 라이더가 플랫폼 앱을 보고 스스로 정한다 | D15 때문에 예정 시각을 받지 않으므로, 계산은 라이더 머릿속에서 한다 |
| 빠른 조회 | 활동 동네 설정, 최근 본 가게, 개인 메모 목록 | '주의 목록'은 개인용으로만 한정할지 검토 |
| 커뮤니티 | 게시판, 가게 연결, 검색 | 운영 규칙 F 적용 |

### 기록하는 것 (D3·D15)

| 항목 | 입력 | 비고 |
|---|---|---|
| 가게 | 지점 선택 | |
| 도착 | [대기 시작] 버튼 | 누른 순간 |
| 픽업 또는 취소 | [픽업]·[취소] 버튼 | 출발 감지 시각과 [픽업] 중 이른 쪽(D14) |
| 출발 감지 | 자동 | 움직임 감지 |
| 메모 | 선택 | 예: "완료 눌렀다는데 음식 없음" |

- **가게 앞 대기 = 픽업(또는 취소) − 도착.** 공유·통계에 쓰는 유일한 시간 지표다.
- 조리 예정 시각, 조리완료 알림 시각, 플랫폼 이름은 **받지 않는다**(D15). 이전 기획의 "약속 초과 = 픽업 − max(예정, 도착)"은 폐기했다. 그 값은 플랫폼 서버에 이미 있으므로(7-2) 필요하면 플랫폼이 확인한다(D7).
- 부수 효과: 가장 입력 부담이 컸던 예정 시각 입력이 사라져, 기록이 [대기 시작]·[픽업] 두 번의 탭으로 줄었다.

### 증거 강도

| 등급 | 무엇 | 누가 만들 수 있나 | 쓰임 |
|---|---|---|---|
| 1. 플랫폼 공식 기록 | 플랫폼이 가진 예정 시각·도착·픽업 기록 | 플랫폼. 라이더는 본인 기록 열람 요청 가능 | 확정 증거 |
| 2. 앱 측정 | 도착·픽업 버튼 시각, 출발 감지. 앱 서버 시각 | 모두 | 가게 앞 대기 시간 |

한 명의 기록은 약해도, 서로 모르는 여러 라이더가 같은 지점에서 비슷한 대기를 남기면 "플랫폼이 자기 기록을 확인해 볼 이유"로는 충분하다(D7).

### 재검토로 빠진 것

- 1~5점 별점, 가게 종합 점수
- 공개 '주의 가게' 순위와 '좋은 가게' 순위

## 5. 부가 기능 (D2, 나중에 검토)

- 디스코드 로그인, 서버 역할 기반 라이더 인증
- 봇 명령어로 가게 조회·기록
- 몇 시간 뒤 사라지는 현장 알림
- 동네 채널 자동 알림
- 채팅 메시지를 기록으로 옮기기

디스코드 연동은 단체 행동을 조직하기 쉬운 통로이기도 하므로, 붙일 때 3장의 치팅 대응을 다시 검토한다.

디스코드가 해결하는 것과 못 하는 것:

| 문제 | 디스코드로 | 이유 |
|---|---|---|
| **누구** (진짜 라이더인가, 모르는 사람이 들어와 지어내나) | ✅ 도움 | 운영진이 확인한 역할만 반영, 커뮤니티 안의 반박과 추방 |
| 한 사람 여러 계정 | ⚠️ 약함 | 이메일만으로 계정을 여럿 만들 수 있다. 전화번호 기반 카카오 로그인(D10)이 더 강하다 |
| **어디** (그 가게 앞에서 눌렀나) | ❌ | 위치를 모른다. 위치 확인(D19)만 가능 |
| 여럿이 짜고 공격 | ❌ 오히려 위험 | 조직하기 쉬운 통로 |

## 7. 조사 결과: 전달 경로와 필요한 증거

> 2026-09-27 웹 조사. 커뮤니티 글은 공식 자료가 아니므로 표시해 둔다.

### 7-1. 플랫폼 신고 창구: 이미 있다

| 플랫폼 | 창구 | 내용 |
|---|---|---|
| 배민 | 배민커넥트 제보센터 (2024년 5월~) | 신고 항목에 **[조리시간 미준수] 조리시간을 준수하지 않아 조리대기가 자주 발생하는 가게**가 있다. 조건: 본인이 수행한 건, **앱에 표시된 조리완료 시간이 지난 뒤**의 대기만 신고 가능. 도입 취지는 "거짓 조리완료를 누르는 가게를 라이더가 직접 신고" |
| 배민 | 커넥트 상담 1600-0220 | "조리완료를 눌렀는데 음식이 안 나온" 경우 상담원 문의 (커뮤니티 안내) |
| 쿠팡이츠 | 고객센터 전화 | 조리 예정 시간보다 5분 지나면 "조리대기 지원금 받고 취소" 요청 가능, 1,000원. 단 콜 취소라 수락률이 내려감 (커뮤니티 정리, 2024년 11월 기준) |

- 신고가 실제로 어떤 조치로 이어졌는지는 공개된 자료를 찾지 못했다. **라이더 경험: 신고해 봤지만 조치 결과를 알 수 없었다.** 신고가 블랙박스라 라이더가 신고할 동기가 약하다.
- **시사점:** 창구는 있지만 한 건씩 개인이 신고하는 구조다. 이 앱은 "이 지점, 서로 다른 라이더 N명, 30일간 평균 대기 M분"처럼 **모아진 신고서**를 만들어 기존 창구의 무게를 키우는 역할을 할 수 있다. 제보센터 조건(예정 시각이 지난 뒤의 대기)에 맞는지는 라이더가 플랫폼 앱의 예정 시각을 보고 판단해 적는다(D15).

### 7-2. 플랫폼 보상 제도: 같은 계산식을 쓴 적이 있다

배민 **픽업 대기 보너스** (2025년 5월 한 달 한정, 확인된 자료 기준)
- 대기 10분 이상 15분 미만 1,000원, 15분 이상 1,500원, 자동 지급
- 측정: **조리완료 예정 시각부터 픽업 완료까지.** 예정 시각 뒤에 도착했다면 도착 시각부터
- 제외: 예정 시각보다 지나치게 일찍 도착한 경우, 가게 반경 100m 밖에서 [도착]·[픽업]을 누른 경우, GPS 조작 등

**시사점:**
- 플랫폼은 가게별 약속 초과를 **이미 자동으로 계산할 수 있다.** 이 앱이 법정 수준 증거를 만들 필요가 없다는 D7이 뒷받침된다.
- 플랫폼도 "반경 100m", "일찍 도착 제외" 같은 치팅 방지 기준을 쓴다. 3-3 대응 B의 참고 기준으로 삼을 수 있다.
- 라이더에게 **플랫폼 [가게 도착] 버튼을 바로 누르라**고 안내하는 것 자체가 도움이 된다. 플랫폼 기록이 곧 1등급 증거이기 때문이다.
- 이 제도가 지금도 운영 중인지는 확인하지 못했다.

**현재 보상 (라이더 경험, 2026-09):** 가게 대기 15분 뒤 **콜을 취소해야** 1,000원을 받는다. 기다렸다가 끝까지 배달하면 받지 못한다.
- 이 구조에서 가게는 잃는 게 없다. 라이더가 취소하면 다음 라이더가 배차되고, 1,000원은 **플랫폼이 낸다.**
- 즉 짧은 조리 예정 시간을 설정한 가게의 비용을 **라이더(시간)와 플랫폼(지원금)이 나눠 떠안는다.** 플랫폼에도 이런 가게를 바로잡을 이유가 있다는 뜻이다. 모아진 신고서에 "이 지점 때문에 발생한 취소 N건"을 넣으면 플랫폼이 움직일 근거가 된다.
- 반대로 1,000원이 15분 손실에 비해 작아서, 라이더가 신고할 동기가 되지는 못한다.

### 7-3. 본인 기록 열람 요청: 가능하지만 느리다

- 개인정보보호법 35조: 본인 개인정보 열람 요구 가능, 처리자는 10일 안에 열람하게 해야 한다.
- 2023년 5월 라이더유니온 조합원 4명이 배민·요기요·쿠팡이츠·바로고에 열람을 요구했다.
  - 네 곳 모두 10일 기한을 지키지 않았다. 요기요·쿠팡이츠·바로고는 **개인정보분쟁조정위원회에 조정을 신청한 뒤에야** 답했다.
  - 받은 것: 쿠팡이츠 배달완료이력, 배민 위치정보(최소 1년 보관), 요기요는 "가게 반경 200m 접근 시각"까지 산출하고 있었다.
  - 못 받은 것: 배차 알고리즘, 수수료·페널티 기준 (영업비밀)
- 2024년 3월부터는 자동화된 결정에 대한 설명요구권이 생겼다.

**시사점:** 도착·픽업 시각 같은 본인 배달 기록은 받을 수 있는 정보로 보인다. 다만 시간이 걸리고 분쟁조정까지 갈 수 있다. 상시 수단이 아니라 **분쟁이 커졌을 때 꺼내는 카드**로 둔다. 앱에서 열람 요구서 양식을 안내하는 정도는 해볼 만하다.

## 8. MVP 범위

### 8-1. 원칙

1. **혼자 써도 쓸모가 있어야 한다.** 실시간 현황과 쌓인 기록은 유저가 늘어야 풍부해진다. 초기에도 개인 도구로서의 가치만으로 앱을 쓸 이유가 있어야 한다.
1-1. **기록이 곧 공유다.** 내가 [대기 시작]을 누르면 따로 조작하지 않아도 동네 현황에 뜬다. 공유를 위한 추가 입력을 만들지 않는다.
2. **법적 위험이 있는 것은 뒤로 미룬다.** 쌓인 가게 기록의 공개(명예훼손·업무방해), 위치 수집(위치정보법), 사진(제3자 개인정보)은 MVP에 넣지 않는다. 실시간 현황은 테스트 그룹 안에서만, 진행 중인 대기만 보여주므로 MVP에 넣는다.
3. **나중에 모을 수 있게 처음부터 제대로 저장한다.** 공개는 안 해도, 2·3단계 집계에 필요한 필드(지점 ID, 플랫폼, 시각, 연장, 결과)는 MVP부터 서버에 남긴다.
4. **도착한 뒤에만 쓴다.** 운전 중 조작을 전제로 하지 않는다. 모든 입력은 가게에 도착해서 기다리는 동안 한다.
5. **음식이 안 나와 있을 때만 쓴다.** 라이더 경험상 피크에도 도착하면 조리가 끝나 있는 경우가 흔하다(라이더가 부족하므로). 대기는 주방이 감당 못 할 만큼 주문이 몰릴 때, 그리고 원래 느린 업장에서 생긴다. 모든 콜을 기록하게 하면 아무도 안 쓴다.
6. **기다리는 동안 하던 걸 방해하지 않는다.** 음식이 안 나와 있으면 라이더는 바로 웹툰이나 유튜브를 켠다. 앱은 그 위에 **떠 있는 작은 타이머**로 남아 있어야 하고, 음식이 나오면 한 번 탭으로 끝나야 한다.

### 8-1-1. 대기 한 건의 흐름

```
도착 → 음식 없음
  → 앱 열고 [대기 시작] (= 도착 시각), 지점은 최근 목록에서 한 번 탭
  → (선택) 알림 시간 정하기: "15분 / 20분 / 25분 뒤 알려줘"
  → 앱이 떠 있는 타이머로 줄어듦 → 웹툰·유튜브 보기
       타이머: "대기 11분"  [픽업] [취소]
       정한 시간이 되면 타이머 색이 바뀌고 진동
  → 음식 나옴: 타이머의 [픽업] 한 번 탭 → 끝
     (깜빡하고 출발하면: 움직임 감지로 출발 시각에 자동 마무리, D14)
```

[대기 시작]부터 끝날 때까지 이 대기는 동네 현황에 "바삭치킨 ○○점 · 1명 대기 중 · 11분째"로 보인다(D12).

- 음식이 바로 나온 콜은 기록하지 않는다. 그래서 "이 지점에 N번 가서 M번 기다림" 같은 비율은 알 수 없다. 대신 **대기가 생겼을 때 얼마나 기다렸는지**만 쌓는다. 비율이 꼭 필요해지면 [바로 받음] 한 번 탭 기록을 나중에 검토한다.
- 알림 시간은 라이더가 플랫폼 앱의 예정 시각을 보고 **스스로 정하는 개인 알람**이다. 앱은 예정 시각을 받지 않는다(D15).

### 8-2. MVP에 넣는 것

> 화면 흐름은 `화면-흐름.md`에 정리했다.


| 기능 | 내용 | 왜 MVP인가 |
|---|---|---|
| 지점 선택 | 지도 장소 검색으로 지점을 고른다. 최근 간 지점을 위에 띄운다 | 자유 입력이면 같은 가게가 여러 이름으로 쌓여 나중에 집계할 수 없다 |
| 대기 타이머 | 음식이 안 나와 있을 때만 [대기 시작] → 지점 선택 → [픽업] 또는 [취소] | D3 지표(가게 앞 대기)의 원천 데이터 |
| **떠 있는 타이머** | 다른 앱(웹툰·유튜브) 위에 작은 타이머로 떠 있음. "대기 11분" 표시, [픽업]·[취소] 바로 탭. 상단 알림에도 같은 타이머와 버튼 | 라이더가 대기 중 실제로 하는 행동(8-1 원칙 6). 이게 없으면 [픽업]을 잊고 기록이 망가진다 |
| 대기 알림 | 라이더가 정한 시간(15/20/25분 뒤 등)이 되면 떠 있는 타이머 색이 바뀌고 진동 | 지원금 타이밍 등을 라이더가 스스로 챙기게 돕는다. 앱은 플랫폼 정보를 쓰지 않는다(D15) |
| 내 기록 | 날짜·지점별 목록, 한 줄 메모. 지점별 내 누적(대기 N회, 평균 대기 M분) | 개인 업무 일지. "이 집 또 이러네"를 숫자로 확인 |

| 신고함 표시 | 기록에 "신고함" 체크와 날짜 | 3단계 개선 추적의 기초 데이터. 지금은 체크만 |
| **실시간 동네 현황** | 활동 동네에서 **확실히 밀린 가게**(D18) 목록. 가게별 대기 인원, 가장 긴 대기, 최근 30분 포기 인원, 기준 시각. 대기가 끝나면 빠짐. 테스트 그룹만 볼 수 있음 | 핵심 가치 ①(D12). 콜을 기다리는 동안 훑어본다 |
| **주고받기 표시** | 최근 7일 기록 여부에 따라 현황을 자세히/간단히 보여줌(첫 2주는 모두 자세히). "오늘 내 기록을 동네 라이더 N명이 봤어요" | 기록 보상(D13) |
| **움직임 감지** | 이동 중 [대기 시작] 막기, 출발 시각 자동 기록 | 데이터 품질(D14) |
| **포기 기록** | 홈의 [안 나와서 그냥 가요] → 가게 한 번 탭. 대기 중 [취소]도 포기로 셈 | 음식이 없으면 바로 떠나는 게 현실이라, 이게 없으면 가장 심한 가게의 데이터가 빠진다(D17) |
| **정차 중 미니 현황** | 대기 중이 아닐 때 폰이 멈춰 있으면 다른 앱 위에 "밀림: 바삭치킨 18분 · 돈까스공방 12분"을 작게 띄움. 이동 중에는 숨김. 누르면 동네 현황으로 | 기다려 봐야 아는 문제를 **가기 전에** 알게 하는 장치(D16). 콜은 몇 초 안에 판단해야 하므로 앱을 열지 않아도 보이게 한다 |

**기록 한 건에 저장하는 것:** 지점 ID, 도착·픽업/취소 시각(앱 서버 시각), 출발 감지 시각, 결과(픽업/취소), 메모, 신고 여부. **플랫폼 정보는 없다(D15).**

### 8-5. MVP로 확인할 가설

| 가설 | 확인 방법 | 실패하면 |
|---|---|---|
| H1. 라이더가 대기가 생길 때마다 기록을 시작한다 | 사용자별 주간 대기 기록 수, 테스트 사용자에게 "기록 안 한 대기" 직접 물어보기 | 지점 선택을 더 줄인다. 예: 자주 가는 가게 고정 |
| H1-1. 떠 있는 타이머로 [픽업]을 제때 누른다 | [대기 시작]만 있고 [픽업]·[취소]가 없는 기록 비율, 픽업이 비정상적으로 늦게 찍힌 비율 | 알림·진동 방식 재검토 |
| H3. 가게 앞 대기 시간이 가게마다 뚜렷이 갈린다 | 테스트 사용자 기록에서 지점별 분포. 라이더에게 "실제로 상습 대기 가게와 일치하나" 물어보기 | D3 지표 재검토 |
| H4. 기록이 신고에 쓰인다 | 신고용 요약 복사 횟수, 신고함 체크 수 | 신고 경로 안내 강화 또는 7장 경로 재검토 |
| H5. 실시간 현황을 보고 판단에 쓴다 | 피크 시간 현황 조회 수, 정차 중 미니 현황을 끈 사용자 비율, 동시에 진행 중인 대기가 있는 시간 비율, 테스트 사용자 인터뷰("현황 보고 콜을 거른 적 있나") | 조회 시점 재설계(콜 알림 연동 검토, 열린 질문 9) 또는 인원 확대 |
| H6. 움직임 감지가 오토바이 출발을 잡는다 | 출발 감지 시각과 [픽업] 시각의 차이 분포, 감지 실패 비율 | 감지 기준 조정, 안 되면 확인 알림 방식으로 후퇴 |
| H8. 음식이 없으면 바로 떠나는 라이더도 포기를 기록한다 | 포기 기록 수 대 대기 기록 수, 인터뷰 | 포기 기록을 미니 현황·떠 있는 알림에서 바로 누르게 |
| H7. 2주 뒤에도 기록한다 (주고받기 효과) | 가입 3주차 이후 주간 기록 사용자 비율 | 문턱·보상 방식 재검토 |

**시작 규모:** 본인과 지인 라이더 10~20명, **한 동네에 집중**, 4주. 실시간 현황은 "한 명이 기다리고 같은 동네의 다른 한 명이 보는" 조건만 채우면 되므로(D12), 여러 동네에 흩어지지 않고 같은 동네·같은 피크 시간에 일하는 사람들로 모은다.

### 8-6. MVP 전에 정할 것

1. ~~**로그인 방식.**~~ → **확정 (D10): 카카오 로그인.** 라이더 인증(열린 질문 3)은 3단계 공개 전까지 미룬다.

   | | 카카오 로그인 | 구글 로그인 | 전화번호 인증 |
   |---|---|---|---|
   | 가입 부담 | 탭 두 번 | 탭 한 번 | 문자 인증 |
   | 다중 계정 | 어려움 (전화번호 인증 계정) | 쉬움 | 어려움 |
   | 비용 | 무료 | 무료 | 문자 건당 비용 |
2. **이용약관의 통계 활용 동의.** 3단계에서 기록을 모아 쓰려면, MVP 가입 때부터 "개인 식별 없이 지점별 통계로 활용"에 동의를 받아 둔다.
3. **웹이냐 앱이냐.** 떠 있는 타이머(원칙 6)는 **웹으로는 만들 수 없다.**

   | | 웹 (PWA) | 안드로이드 앱 | 아이폰 앱 |
   |---|---|---|---|
   | 다른 앱 위에 떠 있기 | 불가 | 가능 ('다른 앱 위에 표시' 권한) | 불가. 대신 잠금화면·다이내믹 아일랜드에 타이머 표시(라이브 액티비티) |
   | 상단 알림에 타이머 + 버튼 | 제한적 (실시간 갱신 어려움) | 가능 | 라이브 액티비티로 가능 |
   | 알림 읽기 자동 기록 (열린 질문 9) | 불가 | 가능 (검토 필요) | 불가 |
   | 배포 | 링크만 주면 됨 | 스토어 심사 또는 설치 파일 | 스토어 심사 |

   **확정 (D9): MVP는 안드로이드 앱으로 만든다.** 라이더 대부분이 갤럭시를 쓰고, 떠 있는 타이머와 알림 읽기가 모두 안드로이드에서만 된다. 테스트 10~20명 단계는 스토어 없이 설치 파일로 나눈다. 아이폰은 라이브 액티비티로 2단계에 붙인다.
4. ~~**지도 장소 검색 API.**~~ → **확정 (D11): 카카오 로컬 API.**

   | | 카카오 로컬 (키워드 장소 검색) | 네이버 지역 검색 |
   |---|---|---|
   | 결과 수 | 페이지 넘기며 여러 개 | 최대 5개, 다음 페이지 없음 |
   | 가게 고유 ID | **있음** → 지점 단위 집계(D5) 가능 | 없음 |
   | 무료 사용량 | 하루 10만 건 (개발자 계정의 첫 카카오맵 앱만) | 하루 2만 5천 건 |
   | 초과 요금 | 건당 2원 | - |

   - 지점 선택: 처음에 **활동 동네**를 한 번 정하고, 그 기준으로 검색. 두 번째부터는 **최근 지점 목록**에서 고른다.
   - 카카오에 없는 가게는 이름·주소로 **직접 추가**하고 "미확인 지점"으로 표시한다.
   - 장소 ID는 폐업·재등록 때 바뀔 수 있으므로, 기록할 때 이름·주소·좌표도 함께 저장한다.
   - 규모가 커져 무료 사용량을 넘기면 검색 결과를 서버에 저장해 재사용한다.
   - 새 카카오 계정을 만들어 무료 사용량을 늘리는 것은 카카오 운영정책(같은 서비스 다수 계정 운영 금지) 위반이므로 하지 않는다.

### 9-2. "외부 유출이 아니면 괜찮은가"

아니다. 쿠팡 약관은 **제3자 제공·공표**뿐 아니라 **복제·저장**과 **업무 외 목적의 사용**도 막는다. 조리 예정 시각을 이 앱에 입력하는 순간, 폰 안에만 두어도 "플랫폼 정보를 다른 앱에서 썼다"고 문제 삼을 수 있다. 그래서 "유출은 안 했다"는 방어에 기대지 않고, **처음부터 받지 않는** 쪽(D15)을 택했다.

신고용 요약에 예정 시각을 넣는 것은 플랫폼 자신에게 보내는 것이라 비교적 안전하지만, 이것도 이 앱이 채우지 않는다. 요약은 빈칸으로 두고 라이더가 신고할 때 플랫폼 앱을 보고 직접 적는다.

### 9-3. 해야 할 것

1. 배민커넥트·쿠팡이츠 앱에서 **현재 약관** 원문 확인: "비밀유지", "정보 보안", "보안 확약서", "정보보호서약서" 조항.
2. 라이더유니온에 **라이더끼리 대기 시간을 공유하는 것**이 약관상 문제되는지 문의. 너무 넓은 비밀유지 조항은 공정위 불공정약관 심사 대상이 될 수 있다(공정위는 배민·쿠팡 약관을 여러 차례 시정시켰다).
3. 2단계 전 변호사 검토: 이 장의 표를 그대로 검토 요청서로 쓴다. 창업 지원 기관, 지자체 무료 법률상담 활용.
4. 2단계 전 위치기반서비스사업 신고 절차 확인(D19).

### 9-4. 명예훼손 성립 요건과 이 앱

사실을 말했다고 무조건 명예훼손이 되지는 않는다.

| 요건 | "○○치킨에서 20분 기다렸다" |
|---|---|
| 여러 사람에게 알림 | 해당 |

위험해지는 경우와 대응: 틀린 사실(정확성 장치, D19), 모욕적 표현(메모 비공개, 숫자만 공개), 낙인(순위 없음, D1), 선동(D4).

**해외 법인은 해결책이 아니다.** 형사 책임은 운영한 사람 개인에게 오고, 한국 사용자·한국 가게 대상이면 한국 법원에서 다툰다. 실제 방어는 설계 원칙, 국내 법인(민사 책임 한정), 배상책임보험, 임시조치 절차 준수, 라이더 단체와의 연대다.

**밖으로 쓰는 말:** "조리대기 가게 거르는 앱"이 아니라 "라이더가 가게 앞 대기 시간을 기록하고 공유하는 앱". 소송에서는 서비스의 목적을 홍보 문구와 운영자의 말까지 증거로 본다.
