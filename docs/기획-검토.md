# 기획 검토

> 상태: 검토 중 · 최종 수정 2026-09-27
> 개발 전 단계. 여기 적힌 기능은 모두 검토 대상이며, 구현 확정이 아니다.

## 1. 배경

배달 라이더가 픽업하는 가게에서 받는 불공정한 대우(조리 지연 방치, 폭언, 파손 책임 전가, 화장실·대기 공간 거부 등)를 개선하기 위한 라이더용 웹 서비스.

### 1-1. 조리 대기가 생기는 구조

> 전업 라이더 2년 경험 기반. 플랫폼 공식 자료로 확인 필요.

- 두 플랫폼(배민·쿠팡이츠) 모두 콜 수락 시 라이더 앱에 **조리 예정 시간**이 뜬다.
- 이 시간은 플랫폼이 추천하고, **가게가 조절할 수 있다.** 설정은 가게 자율이다.
- 조리가 끝나면 가게가 누른 **조리완료 알림**이 라이더에게 뜬다.

문제는 가게가 **소화할 수 없는 짧은 조리 예정 시간을 설정할 때** 생긴다.

| | 정직한 가게 (예: 단골 중국집) | 상습 대기 가게 |
|---|---|---|
| 피크 대응 | 예정 시간을 길게 잡거나 주문을 내림 | 짧게 잡은 채로 콜을 다 받음 |
| 대기 비용 | 가게 앞 마찰로 사장이 직접 치름 | 라이더가 떠안음. 거절하고 가도 다음 라이더가 옴 |
| 라이더에게 하는 말 | - | "조리완료 안 눌렀는데 왜 왔냐" |

짧게 잡는 이유로 추정되는 것: 예정 시간이 길면 라이더가 콜을 거절하고, 고객 앱의 배달 예상 시간도 길어진다.

**핵심:** 느린 것 자체는 문제가 아니다. 피크 때 튀김기 용량처럼 느릴 수밖에 없는 가게도 있다. 문제는 **느린데 빠르다고 알리는 것**이다. 라이더는 가게가 스스로 설정한 시간에 맞춰 배차되어 온 것이므로 "완료 안 눌렀는데 왜 왔냐"는 핑계가 되지 않는다.

## 2. 결정 사항

| # | 결정 | 날짜 |
|---|---|---|
| D1 | 서비스 성격은 **라이더 기록·증거 도구 + 픽업 정보**로 한다. 가게 평가(별점) 서비스로 가지 않는다. | 2026-09-27 |
| D2 | 디스코드 연동은 **부가 기능**으로 분리하고, 메인 기능을 먼저 검토한다. | 2026-09-27 |
| D3 | 핵심 지표는 대기 시간이 아니라 **조리 예정 시간을 넘긴 대기(약속 초과)**로 한다. 정직하게 느린 가게는 보호하고, 짧게 잡아 라이더를 붙잡아 두는 가게를 드러낸다. | 2026-09-27 |
| D4 | 앱은 **정보 제공까지만** 한다. "이 지점 약속 초과 평균 12분"은 되고, "이 가게 거르자"는 안 된다. 콜을 받을지는 라이더 각자 판단한다. | 2026-09-27 |
| D5 | 기록과 공개는 **브랜드가 아니라 지점 단위**로 한다. | 2026-09-27 |

### D1을 고른 이유

|  | 가게 평가 서비스 | 기록·증거 도구 + 픽업 정보 (채택) |
|---|---|---|
| 중심 | 공개 점수, 주의 가게 | 내 대기 기록, 증거, 픽업 위치 정보 |
| 치팅 유인 | 큼. 점수를 깎는 것이 곧 보복 | 작음. 공개되는 것은 모아진 사실뿐 |
| 법적 위험 | 큼 | 작음 |
| 라이더 효용 | 속은 시원함 | 분쟁 때 실제로 도움이 됨 |

공개 정보는 **측정된 대기 시간, 반복적으로 보고된 상황, 픽업 위치** 같은 모아진 사실로 제한한다. 억울한 일에 대한 대응은 **개인 기록·증거를 들고 플랫폼에 정식 신고**하는 쪽으로 유도한다.

## 3. 핵심 위험: 라이더 치팅

가장 큰 우려는 라이더들이 기분이 나쁘다는 이유로 단체로 특정 가게를 공격하거나 보이콧하는 것이다.

### 3-1. 치팅 유형

| 유형 | 예시 | 위험도 |
|---|---|---|
| 단체 보복 | 한 명이 기분 나쁜 일을 겪고 단톡방에서 "다 같이 1점 주자" | 가장 큼 |
| 과장 | 실제 10분 대기를 30분으로 적음 | 중간 |
| 다중 계정 | 한 사람이 계정 여러 개로 도배 | 중간 |
| 앱 밖 보이콧 | 앱의 가게 목록을 근거로 "이 집 콜 받지 말자" 운동 | 큼. 앱이 조직 도구가 됨. D4로 선을 긋는다 |
| 반대 방향 조작 | 가게 측의 자작 호평, 경쟁 가게 악평 | 중간 |

### 3-2. 왜 까다로운가

- **인증으로 해결되지 않는다.** 단체 보복은 진짜 라이더가 한다.
- **정당한 집단 문제 제기와 보복이 데이터상 비슷하다.** 진짜 악질 가게도 문제가 되면 제보가 몰린다. 너무 엄격하면 진짜 피해가 묻힌다.
- **법적 위험이 운영자에게도 온다.** 허위·과장 정보로 가게 영업에 피해가 생기면 명예훼손, 업무방해, 신용훼손 문제가 될 수 있다. 정식 서비스 전에 법률 검토가 필요하다.

### 3-3. 대응 방향

| 방향 | 내용 | 한계 | D1 기준 판단 |
|---|---|---|---|
| A. 별점·순위 폐지, 사실만 기록 | 1~5점 별점과 '주의 가게' 순위를 없애고, 측정된 약속 초과 대기(D3)와 구체적 상황 태그만 남긴다 | 한눈에 판단하기 어렵다 | **채택 방향.** D1과 같은 결론 |
| B. 실제 방문자만 기록 | 대기 타이머 기록 + 가게 근처 위치 확인이 있어야 공개 정보에 반영 | 위치는 조작 가능. 배달 앱 주문 연동은 불가 | 검토 필요 |
| C. 시간 분산 기준 | 서로 다른 날·시간대에 여러 라이더가 겪은 일만 반영. 짧은 기간에 몰린 기록은 보류 후 검토 | 기준 기간·인원 설정이 필요 | **가장 유력.** 진짜 문제는 흩어져 쌓이고, 보복은 몰린다 |
| D. 기록자 신뢰도 | 여러 가게를 골고루, 좋은 가게도 기록하는 사람에게 가중치. 신규·편향 계정은 낮춤 | 기준이 불투명하면 불만 | 검토 필요 |
| E. 판결이 아닌 기록으로 표시 | "주의"라는 낙인 대신 "최근 30일 기록 12건, 평균 대기 18분" 형태. 오래된 기록은 점점 흐려짐. 가게 측 해명·정정 창구 | 운영 부담 | 채택 방향 |
| F. 운영 규칙 | "다 같이 콜 거절하자" 같은 집단 행동 선동 금지. 이상 패턴 자동 보류, 신고 누적 시 가림 | 운영 인력 필요 | 채택 방향 |

## 4. 메인 기능 후보 (D1 기준 재검토 대상)

라이더가 앱을 여는 세 순간을 기준으로 삼는다.

| 순간 | 상황 | 필요한 것 |
|---|---|---|
| 배차 수락 전, 픽업 가는 길 | 몇 초, 한 손 조작 | 어디로 픽업 가는지, 대기가 긴 편인지 |
| 가게 도착 후 대기 중 | 몇 분씩 붙잡혀 있음 | 기록하기 |
| 퇴근 후 | 여유 있음 | 커뮤니티, 내 기록 돌아보기 |

| 후보 | 내용 | 비고 |
|---|---|---|
| 대기 타이머 + 내 기록 | 아래 네 시각을 기록해 약속 초과를 계산. 사진·메모 첨부, 개인 업무 일지로 누적 | D1·D3의 중심 기능. 치팅 대응 B의 근거 데이터 |
| 픽업 정보 | 픽업 위치, 주차 위치, 화장실 가능 여부 등을 라이더들이 함께 채움 | 사실 정보라 법적 위험이 적음 |
| 가게 정보 (모아진 사실) | 시간대별 평균 대기, 반복 보고된 상황. 별점·순위 없음 | 치팅 대응 C·E 적용 필요 |
| 신고용 기록 정리 | 내 기록을 날짜·시각·대기·사진 요약으로 정리해 고객센터에 붙여넣기 | 대처법 체크리스트와 연결 |
| 빠른 조회 | 활동 동네 설정, 최근 본 가게, 개인 메모 목록 | '주의 목록'은 개인용으로만 한정할지 검토 |
| 커뮤니티 | 게시판, 가게 연결, 검색 | 운영 규칙 F 적용 |

### 기록할 시각 (D3)

| 시각 | 입력 방법 (검토) | 비고 |
|---|---|---|
| ① 조리 예정 시각 | 콜 수락 시 앱에 뜬 시간을 입력. 콜 화면 캡처 첨부 가능 | 증거의 기준점. 캡처가 있으면 가장 강함 |
| ② 도착 | [도착] 버튼 | |
| ③ 조리완료 알림 | [완료 알림 옴] 버튼 (선택) | 알림 후에도 못 받았는지 확인용 |
| ④ 픽업 | [픽업] 버튼 | |

- **약속 초과 = ④ − max(①, ②)**. 예정 시각 전에 일찍 도착해서 기다린 시간은 라이더 몫이므로 빼고, 예정 시각이 지난 뒤의 대기만 센다.
- ③ 이후에도 대기가 길면 "완료를 누르고도 음식을 내주지 않음"이라는 별도 신호가 된다.
- 입력 부담이 가장 큰 것은 ①이다. 도착 후 대기 중에 입력해도 되게 한다.

### 재검토로 빠진 것

- 1~5점 별점, 가게 종합 점수
- 공개 '주의 가게' 순위와 '좋은 가게' 순위

## 5. 부가 기능 (D2, 나중에 검토)

- 디스코드 로그인, 서버 역할 기반 라이더 인증
- 봇 명령어로 가게 조회·기록
- 몇 시간 뒤 사라지는 현장 알림
- 동네 채널 자동 알림
- 채팅 메시지를 기록으로 옮기기

디스코드 연동은 단체 행동을 조직하기 쉬운 통로이기도 하므로, 붙일 때 3장의 치팅 대응을 다시 검토한다.

## 6. 열린 질문

1. 가게 정보를 공개하는 최소 기준(기간, 인원, 서로 다른 날짜 수)을 어떻게 정할까?
2. 공개 정보에 '반복 보고된 상황' 태그를 넣을지, 대기 시간과 픽업 정보만 공개할지?
3. 라이더 인증 방식(디스코드 역할 / 캡처 인증 / 본인인증)을 어디까지 할까?
4. 가게 측 해명·정정 창구를 처음부터 둘까?
5. 서비스 이름
6. 가게가 콜 수락 **이후에** 조리 예정 시간을 늘릴 수 있는가? 늘릴 수 있다면 라이더 앱에 바뀐 시간이 뜨는가? (① 기준점이 바뀌므로 확인 필요)
7. 조리 예정 시간 설정 기능을 플랫폼 사장님용 공식 안내로 확인할 수 있는가? (1-1 검증)
8. 수락률 관리 때문에 라이더가 콜을 마음대로 거절하기 어렵다면, 정보만으로는 가게에 압박이 가지 않는다. 쌓인 기록을 **플랫폼 신고나 라이더 단체**로 전달하는 경로를 메인에 넣을까?
