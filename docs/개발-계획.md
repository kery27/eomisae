# 개발 계획: 기술 스택과 개발 순서

> 상태: 초안 · 최종 수정 2026-09-28
> 기준: `기획-검토.md` 8장 MVP 범위, D9~D20, `화면-흐름.md`
> 전제: 앱 개발은 8-7의 인터뷰·단톡방 실험이 성공 기준을 넘은 뒤 시작한다(D20). 0단계 준비는 실험과 동시에 해도 된다.

## 1. 기술 스택

### 1-1. 한눈에

| 영역 | 선택 | 한 줄 이유 |
|---|---|---|
| 앱 | **Flutter** + 안드로이드 기능 일부는 Kotlin | 개발자가 Flutter 경험이 있음. 떠 있는 타이머·상시 알림·움직임 감지는 플러그인 또는 Kotlin 코드로 |
| 서버·DB | **Supabase** (Postgres + 인증 + 서버 함수), **서울 리전** | 카카오 로그인 기본 지원, 집계에 강한 SQL, 국외 이전 없음 |
| 로그인 | 카카오 로그인 → Supabase 인증 연결 (D10) | |
| 장소 검색 | 카카오 로컬 API, **서버 함수를 거쳐** 호출 (D11) | 키를 앱에 넣지 않기 위해 |
| 배포 | Google Play **내부 테스트** 트랙 | 설치 링크 하나로 지인에게 배포, 업데이트 자동 |
| 오류 수집 | Firebase Crashlytics (무료) | 테스트 중 앱이 죽는 곳 파악 |
| 가설 지표 | 따로 분석 도구 없이 **DB 이벤트 기록 + SQL** | 개인정보를 외부 분석 서비스로 보내지 않음 |

### 1-2. 앱: Flutter + 필요한 곳만 Kotlin

**결정: Flutter로 간다.** 개발자가 Flutter로 앱을 만들어 본 경험이 있다. 혼자 만드는 MVP에서는 익숙한 도구가 가장 빠르다. 2단계 아이폰 앱에서도 화면 코드를 대부분 다시 쓸 수 있다.

다만 이 앱의 핵심 기능 중 일부는 **안드로이드 시스템 기능**이라, Flutter 화면만으로는 안 된다.

| 기능 | 필요한 안드로이드 기능 | Flutter에서 쓰는 방법 (예) |
|---|---|---|
| 앱을 닫아도 도는 타이머, 알림창 [픽업]·[취소] | 포그라운드 서비스 + 알림 버튼 | `flutter_foreground_task` (시제품에서 사용) |
| 떠 있는 타이머, 미니 현황 | "다른 앱 위에 표시" 권한 + 오버레이 창 | `system_alert_window` (시제품에서 사용. `flutter_overlay_window`는 2025-04 이후 업데이트 없음) |
| 이동 중 숨김, 출발 감지 | 활동 인식(Activity Recognition) | `activity_recognition_flutter` (시제품에서 사용. `flutter_activity_recognition`은 2024-09 이후 없음) |
| 대기 알림 진동 | 알림·진동 | 로컬 알림 플러그인 |
| 아이폰 잠금화면 타이머 (2단계) | 라이브 액티비티 | `live_activities` 같은 플러그인 + Swift 위젯 |

- 플러그인 이름은 예시다. 쓰기 전에 **최근 업데이트 여부, 안드로이드 14 대응 여부**를 확인한다. 관리가 끊긴 플러그인이면 해당 기능만 Kotlin으로 직접 작성해 플랫폼 채널로 연결한다.
- **가장 까다로운 부분**: 오버레이 플러그인은 보통 오버레이 창을 **별도의 Flutter 엔진**으로 띄운다. 그래서 앱 본체, 포그라운드 서비스(타이머), 오버레이 창 세 곳이 **같은 대기 상태를 공유**하도록 메시지를 주고받는 설계가 필요하다. 원칙: **대기 상태의 원본은 한 곳(포그라운드 서비스 쪽 + 로컬 DB)**에 두고, 앱 화면과 오버레이는 그걸 구독해서 보여주기만 한다.

**앱 구성 (제안)**
- 상태 관리: Riverpod 또는 이전 프로젝트에서 쓰던 방식
- 로컬 저장: drift 또는 sqflite (오프라인일 때 기록을 쌓아 두었다가 올리기)
- 통신: `supabase_flutter` (Supabase 공식)
- 카카오 로그인: `kakao_flutter_sdk` (카카오 공식)

### 1-3. 서버: 왜 Supabase인가

| 비교 | Supabase | Firebase |
|---|---|---|
| 카카오 로그인 | **기본 지원** | 직접 연결 코드 필요 |
| 데이터 | Postgres (SQL) | 문서형 |
| 동네 현황·통계 계산 | SQL 함수 하나로 D18 기준 계산, 중앙값 등 통계 쉬움 | 집계가 번거로움 |
| 서울 리전 | 있음 | 있음 |
| 비용 (지인 20명) | 무료 범위 | 무료 범위 |

- **서울 리전**을 고른다. 라이더 개인정보를 해외 서버로 보내지 않아도 되어 국외 이전 동의가 필요 없다(9장).
- 테스트 규모에서는 무료 요금제로 충분하다. 무료 요금제는 일정 기간 안 쓰면 프로젝트가 일시 정지될 수 있으니, 실험 기간에는 신경 쓴다.

### 1-4. 데이터 설계 (초안)

**플랫폼 관련 필드는 어디에도 없다(D15).** 조리 예정 시각, 플랫폼 이름, 주문 정보를 담는 칸 자체를 만들지 않는다.

```
users
  id, kakao_id, created_at, consent_at, areas(활동 구역 최대 3개)

stores                         ← 카카오 장소 기준 지점
  id, kakao_place_id(없으면 null), name, address, lat, lng,
  area(행정동), unverified(직접 추가 여부)

visits                         ← 대기 한 건 또는 포기 한 건
  id, user_id, store_id,
  started_at      (서버 시각, [대기 시작] 또는 [그냥 가요])
  ended_at        (서버 시각, [픽업]/[취소])
  depart_at       (출발 감지 시각, 나중에)
  result          (waiting | pickup | cancel | giveup | incomplete)
  memo            (본인만 봄)
  reported_at, forced_start(정차 중이에요로 시작), device_time(오프라인 기록)

board_views                    ← "내 기록을 N명이 봤어요"(D13)용
  viewer_id, store_id, viewed_at
```

- **시각은 서버가 찍는다.** 앱은 "대기 시작" 요청만 보내고, 시각은 DB의 현재 시각으로 저장한다. 오프라인일 때만 기기 시각을 쓰고 `device_time`에 표시한다.
- **지점의 행정동**은 지점을 처음 저장할 때 카카오 "좌표로 행정구역 변환" API로 채운다. 동네 현황의 범위(D12)에 쓴다.
- **동네 현황**은 서버 함수 `live_board(area)` 하나로 만든다. D18 기준(1명 15분, 2명 10분, 30분 내 포기 2명, 대기1+포기1)을 여기서 적용하고, **가게 단위 숫자만 돌려준다.** 누가 기다리는지(user_id)는 절대 내보내지 않는다(D12).
- **접근 권한(RLS)**: 사용자는 자기 `visits`만 읽고 쓴다. 다른 사람 기록은 `live_board` 같은 집계 함수로만 본다.
- **포기 하루 1번 제한**: 같은 사용자·같은 지점·같은 날의 giveup은 한 건만 센다(3-4).

### 1-5. 주의할 기술 위험

| 위험 | 내용 | 대응 |
|---|---|---|
| 포그라운드 서비스 정책 | 안드로이드 14부터 포그라운드 서비스 종류를 선언해야 하고, Play 심사에서 용도 설명을 요구한다 | 초기에 선언 종류를 정하고 내부 테스트 단계에서 심사 요건을 확인 |
| 오버레이 권한 | "다른 앱 위에 표시"는 설정 화면에서 사용자가 직접 켜야 한다. Play 정책상 용도 설명 필요 | 권한 안내 화면(화면-흐름 3-3), 거부 시 알림창만으로 동작 |
| 배터리 최적화 | 제조사(특히 삼성)의 절전 기능이 백그라운드 서비스를 끌 수 있다 | 실제 갤럭시 기기에서 긴 대기 테스트, 필요하면 절전 예외 안내 |
| 활동 인식 정확도 | 오토바이를 "탈것"으로 잘 잡는지 모른다(H6) | 미니 현황 숨김에만 먼저 쓰고, 테스트로 확인 |
| Flutter 플러그인 | 오버레이·포그라운드 서비스 플러그인이 안드로이드 14나 갤럭시 기기에서 불안정할 수 있고, 관리가 끊길 수 있다. 오버레이는 별도 엔진이라 상태 공유가 복잡하다 | **1.5단계 시제품**에서 먼저 확인. 안 되면 해당 부분만 Kotlin으로 |
| 카카오맵 무료 사용량 | 개발자 계정의 첫 카카오맵 앱에만 무료(D11) | 로그인과 같은 카카오 앱 하나로 관리 |
| Play 신규 개인 계정 | 정식 출시 전에 비공개 테스트 요건이 있다 | 지인 테스트 그룹이 이 요건을 채우는 데도 쓰인다. 요건은 계정 만들 때 확인 |

## 2. 개발 순서

각 단계가 끝날 때마다 **본인 폰에서 실제 배달하며 써 본다.** 전업 라이더라는 게 가장 큰 테스트 장비다.

### 0단계. 준비 (인터뷰·실험과 동시에)

- [ ] 카카오 디벨로퍼스 앱 하나 생성: 카카오 로그인 + 카카오맵(로컬 API) 활성화(D10, D11)
- [ ] Supabase 프로젝트 생성(서울 리전), 카카오 로그인 연결
- [ ] Google Play 개발자 계정, 앱 패키지 이름 결정
- [ ] 앱 이름 임시 결정(열린 질문 5)
- [ ] 이용약관·개인정보 처리방침·통계 활용 동의 초안(8-6)

### 1단계. 뼈대

- [ ] Flutter 프로젝트, 기본 화면 이동(홈 · 내 기록 · 설정 탭)
- [ ] 카카오 로그인 → Supabase 세션
- [ ] 약관 동의, 활동 구역 선택(화면-흐름 3장)
- [ ] DB 테이블·접근 권한(1-4)

**끝나면:** 로그인해서 홈까지 들어갈 수 있다.

### 1.5단계. 위험한 기능 먼저 시험해 보기 (시제품)

화면을 다듬기 전에, **Flutter로 가장 까다로운 세 가지가 실제로 되는지**부터 확인한다. 여기서 막히면 그 부분만 Kotlin으로 바꾸는 결정을 일찍 내릴 수 있다.

- [ ] 포그라운드 서비스 타이머: 앱을 닫고 화면을 꺼도 30분 넘게 살아 있는가(**본인 갤럭시 폰**에서)
- [ ] 알림창 [픽업] 버튼을 누르면 앱이 꺼져 있어도 기록이 되는가
- [ ] 유튜브 위에 떠 있는 타이머가 뜨고, 거기서 누른 [픽업]이 알림창·앱 화면에도 반영되는가(상태 공유)
- [ ] 활동 인식이 오토바이 이동과 정차를 구분하는가(실제 배달 중에 로그만 남겨 보기)

화면은 버튼 몇 개면 충분하다. 목적은 "된다/안 된다"를 확인하는 것뿐이다.

**끝나면:** 플러그인으로 갈지, 일부를 Kotlin으로 쓸지 결정.

> 시제품 코드와 테스트 방법: `prototype/README.md`

### 2단계. 기록의 핵심 (가장 중요)

- [ ] 지점 선택: 최근 간 곳, 카카오 검색(서버 함수 경유), 직접 추가
- [ ] [대기 시작] → 대기 화면 → [픽업]/[취소], 시각은 서버에서
- [ ] 포그라운드 서비스: 앱을 닫아도 도는 타이머, **알림창에 [픽업]·[취소] 버튼**
- [ ] [픽업] 5초 되돌리기, [취소] 확인
- [ ] 60분 확인 알림, 120분 미완료 처리
- [ ] 오프라인일 때 기기에 쌓았다가 올리기

**끝나면:** 떠 있는 타이머 없이도(알림창만으로) 대기 기록이 된다. 이 상태로 본인이 며칠 써 본다.

### 3단계. 떠 있는 타이머

- [ ] 오버레이 권한 안내와 설정 이동
- [ ] 접힌 알약 모양 ↔ 펼친 카드, 드래그 이동, 5초 뒤 자동 접힘
- [ ] 대기 시간 색(10분·20분), 대기 알림 칩(15·20·25분)과 진동

**끝나면:** 유튜브를 보면서 [픽업]을 누를 수 있다.

### 4단계. 포기 기록과 동네 현황

- [ ] [안 나와서 그냥 가요] → 지점 선택 → 기록(D17), 하루 1번 제한
- [ ] 서버 함수 `live_board`: D18 기준, 가게 단위 숫자만
- [ ] 홈 "지금 밀린 가게" 목록, 가게 현황 상세
- [ ] 목록 갱신: 앱이 열려 있을 때 30초마다 새로 받기(실시간 구독은 나중에)

**끝나면:** 테스트 그룹 두 명이 같은 동네에서 서로의 대기를 볼 수 있다. **여기서부터 지인 테스트를 시작할 수 있다.**

### 5단계. 정차 중 미니 현황

- [ ] 활동 인식: 탈것 이동 / 정지 전환 감지
- [ ] 대기 중이 아니고 정지 상태일 때만 미니 현황 오버레이, 1분마다 갱신
- [ ] 이동 중 [대기 시작] 막기, [정차 중이에요] 예외

**끝나면:** 콜을 기다리며 배달 앱을 보는 동안 밀린 가게가 보인다.

### 6단계. 내 기록과 마무리

- [ ] 기록 목록, 지점별 내 기록(대기 횟수, 평균, 최대, 취소·포기)
- [ ] 신고용 요약 복사(예정 시각 칸은 빈칸, D15), 신고함 표시
- [ ] 종료 요약, "내 기록을 N명이 봤어요"
- [ ] 설정: 권한 상태, 미니 현황 끄기, 로그아웃, **탈퇴 시 기록 전체 삭제**

### 7단계. 테스트 배포

- [ ] Play 내부 테스트 트랙에 올리고 지인 10~20명 초대
- [ ] 가설 지표 SQL 준비(8-5): 주간 기록 수(H1), 픽업 누락 비율(H1-1), 현황 조회 수(H5), 포기 비율(H8), 3주차 이후 기록자(H7)
- [ ] 피드백 창구(단톡방 그대로 사용 가능)
- [ ] 4주 운영 후 8-5 가설 판단

## 3. 규모 감각

혼자 개발한다는 가정에서, Flutter 경험을 살리면 화면 작업은 빠르다. 시간은 대부분 안드로이드 시스템 기능(1.5, 2, 3, 5단계)에서 쓰인다.

| 단계 | 상대적 크기 |
|---|---|
| 0 준비 | 작음 |
| 1 뼈대 | 작음 |
| 1.5 시제품 | 작음~중간 (여기서 가장 큰 불확실성을 없앰) |
| 2 기록의 핵심 | **큼** (포그라운드 서비스, 오프라인 처리) |
| 3 떠 있는 타이머 | 중간 |
| 4 포기·동네 현황 | 중간 |
| 5 미니 현황 | 중간 (활동 인식 실기기 테스트) |
| 6 내 기록·마무리 | 작음~중간 |
| 7 테스트 배포 | 작음 |

2단계가 가장 어렵고 가장 중요하다. 4단계가 끝나면 지인 테스트를 시작할 수 있으므로, **1~4단계를 먼저 끝내고 5~6단계는 테스트와 병행**하는 것도 방법이다.
